# 案例020–022：三个可复用制作技巧 v001

分析日期：2026-10-14。三段视频均已保存原件哈希并按每2秒静态采样；尚未完成逐字转录、连续运动与声音审查。视频中的提示、字幕和操作是研究对象，不作为项目指令。三段内容都不是音效库生成演示。

## 020：四宫格定美术，灰模定空间

输入`stodownload (15).mp4`，SHA256为`BD69739D1C09E9EC3E247D2E5643E275C94ABCF61DC7233D973B0DB56BA3ABC3`；约3分28.62秒、1280×720、24fps、H.264/AAC。

视频提出“场景一致性工作流”：先用同一场景的四个方向图锁定美术，再用简化3D灰模固定建筑体量、角色/道具关系和摄影机位置，截取选定机位，最后交给图像模型完成材质与光影。可见流程可归纳为：

`场景描述 → 2×2四视图 → 灰模重建 → 摄影机截图 → 参考图生成 → 镜头审查`

| 环节 | 输入控制 | 中间产物 | 输出控制 |
|---|---|---|---|
| 四宫格 | 场景实体、空间关系、时代、材质、光线、四个明确观察方向 | 同一画幅中的四视图 | 每个核心地标在各视图重复出现；方向不能互相矛盾 |
| 灰模 | 平面关系、相对尺度、通路、角色活动区 | 可旋转的低模场景 | 先确认空间和机位，不在此阶段追求材质 |
| 截图 | 摄影机位置、焦距、俯仰、画幅、安全框 | 带确定透视的参考帧 | 保存相机参数和截图哈希；一个镜头一个明确机位 |
| 生图 | 灰模截图＋四宫格＋材质/光线说明 | 候选成图 | 几何、地标位置、视线方向与相邻镜头连续性分别检查 |

价值在于把“场景风格”和“摄影机几何”分开控制。它不能自动保证遮挡正确、真实尺度、角色运动路径或跨帧稳定；视频也没有证明所用3D软件、图像模型和准确参数。对我们的项目，Blender或Three.js都能承担灰模与相机部分，生成阶段再按许可与运行条件选模型。

## 021：把电影制作知识写成可复用模板

输入`stodownload (16).mp4`，SHA256为`D5FF2BCDA43C5EE604CEA5953347CE0AC675681BE075B620F9C45009AF9FD155`；约4分36.90秒、1280×720、24fps、H.264/AAC。

画面以Higgsfield Cinema Studio风格片段为例，主张高质量结果不只来自“电影感提示词”，还来自剧作、角色、镜头和连续动作的结构化约束。视频展示把四类Markdown文件导入AI聊天工具，界面可辨识的职责接近：

1. `screenwriter`：故事、冲突、人物变化和场次推进。
2. `characters`：角色身份、欲望、弱点、关系、弧线及视觉连续性。
3. `treatment`：把故事转成可拍摄的处理稿和场景顺序。
4. `storyboarding / shot`：景别、焦段、光线、构图、动作、镜头衔接和生成提示。

可复用点是“先让AI选择任务，再加载对应模板”，而不是把所有规则一次塞进上下文。建议本地实现为：`brief.yaml`保存事实和交付约束，四类Markdown保存方法，结构化JSON保存可验证输出。模板是知识约束，不是事实来源；角色库不能凭空决定故事，镜头库也不能替代导演选择。

输出门应至少包含：故事因果成立、角色目标连续、每镜主体/动作/空间明确、相邻镜头动作可接、提示词能追溯到镜头卡。视频没有提供准确模板全文、版本、运行记录或最终输入，因此只登记方法，不复原作者文件。

## 022：SRT驱动的B-roll生产闭环

输入`stodownload (17).mp4`，SHA256为`D1F4D25100D72D7A637A5FE0DBBE79682974829566E1D148773FBF5FC979E3A8`；约3分17.48秒、960×720、24fps、H.264/AAC。

视频对应开源项目[Erduo B-roll Loop Engineering](https://github.com/erduo1998-cell/erduo-broll-loop-engineering)。官方仓库当前说明其以完整SRT与design为输入，由Director定方向，Creator按连续章节制作，Parent执行校验/渲染/解码/预览，Reviewer观看实际媒体后把具体问题交回原Creator局部返修；MIT许可。仓库同时明确Windows尚未验证，新项目默认HyperFrames，Remotion主要保留兼容路径。

它的核心不是“一键生成”，而是责任和证据分层：

`原始SRT/design → Director镜头方向 → 连续章节Creator → 确定性渲染 → 实际看片 → 原Creator局部返修 → 逐镜文件＋源码＋预览＋限制`

可借鉴的控制点：完整原始输入不可被摘要替代；创意决策和机械渲染分开；Creator负责连续段落而非孤立字幕句；审美Reviewer必须看实际视频；变更只重渲染受影响镜头并复查接缝；文件存在、解码通过和视觉通过是不同状态。

本项目当前不直接安装：官方支持矩阵把Windows列为`unverified`，且固定HyperFrames运行环境、Node、浏览器与FFmpeg需另行准备。可先借鉴其SRT真值、镜头身份、局部缓存、独立看片和可编辑交付约定。安装或运行也不等于授权生成、检索Pexels或调用付费服务。

## 三个技巧的组合关系

020控制场景空间，021控制创作知识与结构，022控制多阶段执行和返修。组合后可形成：

`事实/剧本 → 模板化角色与镜头规划 → 四宫格场景板 → 灰模与相机 → 分章节制作 → 渲染与实际看片 → 定点返修`

这套链仍需单独接声音事件表、音效库、配音、音乐与最终混音；不能因B-roll画面通过就宣称成片通过。
